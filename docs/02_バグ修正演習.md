# 02. バグ修正演習(Phase 2: 直す)

このPhaseでは、バグが仕込まれた演習用ブランチに切り替えて、**実務風のバグチケット5件**に取り組みます。「動かないコードを、症状から出発して直す」体験がゴールです。

所要時間の目安: 6〜10時間(1チケット1〜2時間。BUG-01から順に難しくなります)

---

## 1. 演習用ブランチに切り替える

```bash
git checkout exercise/bugs      # バグ入りブランチへ
./gradlew run                   # まず普通に起動できることを確認
```

チケットごとに作業ブランチを切っておくと、やり直しがしやすくおすすめです。

```bash
git switch -c fix/bug-01        # 例: BUG-01用の作業ブランチ
```

> **重要なお願い**: `git diff main` を実行すれば、仕込まれたバグの答えが一目で分かってしまいます。しかし**それは最終手段にしてください**。実務で遭遇するバグに「正解とのdiff」は付いてきません。このPhaseの価値は、症状から原因へたどり着く過程にあります。

## 2. 演習の進め方 — 6つのステップ

どのチケットも、次のサイクルで進めます。実務のバグ修正とほぼ同じ流れです。

1. **症状を再現する** — チケットの再現手順どおりに操作し、自分の目で症状を確認します。再現できないバグは直せません。
2. **仮説を立てる** — 「どの層の、どのあたりのコードが怪しいか」を紙に書きます。Phase 1の地図(UI→Service→Repository)が武器になります。
3. **検証する** — デバッガ・ログ・テスト・print文などで仮説を確かめます(道具の使い方は後述)。
4. **修正する** — 原因が特定できたら、**最小限の変更**で直します。ついでのリファクタリングは我慢しましょう。
5. **再発防止テストを追加する** — 「このバグがまた起きたら赤くなるテスト」を書きます(可能なもののみ。BUG-04とBUG-05は自動テストが難しいため、代わりに手動確認手順をコメントやメモとして残します)。
6. **answersと照合する** — 修正が終わったら(あるいは2時間悩んでお手上げなら)`docs/answers/bug-0X.md` で答え合わせをします。**開く前に、自分の仮説を必ず言語化しておくこと。**

修正後は毎回 `./gradlew test` を実行し、**他のテストを壊していないこと**も確認してください。

## 3. 道具の使い方入門

### 3-1. スタックトレースの読み方

プログラムが例外で落ちると、コンソールに次のような出力(スタックトレース)が出ます。

```
Exception in thread "main" java.lang.NumberFormatException: For input string: "abc"
	at java.base/java.lang.Integer.parseInt(Integer.java:652)
	at com.example.demo.PriceCalculator.parsePrice(PriceCalculator.java:25)
	at com.example.demo.PriceCalculator.main(PriceCalculator.java:10)
```

読み方のコツは3つです。

1. **1行目**が「何が起きたか」。例外の種類(NumberFormatException=数値変換の失敗)とメッセージ(`"abc"` を変換しようとした)。
2. **`at` の行**は呼び出しの積み重ねで、**一番上が例外の発生地点**。下に行くほど呼び出し元です(mainから始まってparsePriceが呼ばれ、その中のparseIntで落ちた)。
3. まず**自分のコード(`com.example.kakeibo` で始まる行)の中で一番上のもの**を探してください。JDKやライブラリの行(`java.base/...`)は読み飛ばして構いません。行番号付きなので、その行を開くのが第一歩です。

`Caused by:` が続く場合は、そちらが**元々の原因**です(例外が別の例外を包んでいる状態。このアプリのDataAccessExceptionがまさにそれです)。

### 3-2. デバッガ(ブレークポイントとステップ実行)

デバッガは「プログラムを一時停止して、変数の中身を覗く」道具です。IntelliJ IDEAの場合:

1. 止めたい行の行番号の右側をクリック → 赤い丸(**ブレークポイント**)が付く
2. `Main.java` を右クリック → **Debug 'Main.main()'** で起動
3. その行を通る操作をアプリ上で行うと、実行が一時停止する
4. 下部のパネルで**変数の値**を確認できる
5. ボタンで少しずつ進める:
   - **Step Over(F8)**: 次の行へ(メソッド呼び出しの中には入らない)
   - **Step Into(F7)**: 呼び出したメソッドの中に入る
   - **Resume(F9)**: 次のブレークポイントまで再開

「Serviceに渡ってきた値はもう壊れているか?それともまだ正しいか?」のように、**層の境界にブレークポイントを置いて値を確かめる**のが、3層アプリの定石です。

### 3-3. テストとログ

- `./gradlew test` — 既存のテストが症状を検知していないか、まず最初に実行する価値があります。
- このアプリは `java.util.logging` でログを出しています。エラー時のスタックトレースはコンソールに出るので、必ず拾ってください。

## 4. バグチケット

> どのチケットも「バグはこのリポジトリのJavaコードのどこか1〜2箇所」にあります。ライブラリやデータのせいではありません。

### チケット BUG-01

```
チケット番号: BUG-01
報告者      : 経理担当・佐藤
症状        : 使わなくなったカテゴリを削除しようとしたら、アプリがエラーで固まった
再現手順    : 1. メニューから「カテゴリ管理」を開く
              2. 取引で使用中のカテゴリ(例: 食費)を選ぶ
              3. 「削除」ボタンを押し、確認で「はい」を選ぶ
期待動作    : 「使用中のため削除できません」と案内され、アプリは正常に動き続けること
ヒント      : まず ./gradlew test を実行してみてください
必須タスク  : 修正後、再発防止テストが緑になることを確認する(このバグは既存テストが検知します。
              なぜ検知できたのかも考えてみてください)
```

### チケット BUG-02

```
チケット番号: BUG-02
報告者      : 利用者・田中
症状        : 金額に「1,000」とカンマ付きで入力して保存したら、エラーで落ちた。
              以前は登録できていた気がする
再現手順    : 1. 「登録」ボタンで取引登録ダイアログを開く
              2. 金額欄に「1,000」(カンマ付き)と入力し、他の項目も埋める
              3. 「保存」ボタンを押す
期待動作    : 1000円の取引として登録されること
ヒント      : エラーが起きた瞬間、コンソールに何が出ていますか。
              スタックトレースの読み方(このドキュメントの3-1)を使ってください
必須タスク  : 修正後、再発防止テストを追加する。
              「このバグはなぜ ./gradlew test をすり抜けたのか?」への自分なりの答えをメモする
```

### チケット BUG-03

```
チケット番号: BUG-03
報告者      : 利用者・鈴木
症状        : 5月31日に使ったお金が、5月の月次集計に入っていない。
              一覧画面で5月に絞ると、ちゃんと表示されるのに
再現手順    : 1. 一覧画面のフィルタで「2026年5月」を選び、支出合計をメモする(ステータスバー)
              2. メニューから「月次集計」を開き、「2026年5月」を選ぶ
              3. 集計画面の支出合計が、手順1の金額より少ないことを確認する
期待動作    : 一覧のフィルタ結果と月次集計で、同じ月の支出合計が一致すること
ヒント      : ./gradlew test は全部緑です。「テストが緑=バグがない」ではありません。
              一覧と集計、それぞれの絞り込みがどう実装されているか見比べてください
必須タスク  : 修正後、このバグを検知できる再発防止テストを追加する
              (なぜ既存テストが素通りさせたのかを、テストコードを読んで確かめること)
```

### チケット BUG-04

```
チケット番号: BUG-04
報告者      : 利用者・高橋
症状        : 取引を編集して保存しても、一覧の表示が変わらない。
              ただし、アプリをいったん終了して起動し直すと、変更後の内容になっている
再現手順    : 1. 一覧で取引をひとつ選び「編集」を押す
              2. 金額を変更して「保存」を押す
              3. 一覧の金額が変わっていないことを確認する
              4. アプリを再起動すると、変更が反映されていることを確認する
期待動作    : 保存した直後に、一覧へ変更内容が反映されること
ヒント      : 「再起動すると直っている」が最大の手がかりです。
              データ(DB)と表示(画面)のどちらの問題かを、まず切り分けてください
必須タスク  : このバグの自動テストは難しいため、代わりに「手動確認の手順」を
              自分の言葉で書き残す(どう操作すれば再発に気づけるか)
```

### チケット BUG-05

```
チケット番号: BUG-05
報告者      : 利用者・伊藤
症状        : 月次集計を開くと、画面全体が数秒〜数十秒固まって操作できなくなる。
              データを増やしてから急に遅くなった。少ないうちは気にならなかった
再現手順    : 1. docs/04_大量データ投入.md の手順で、5万件のダミー取引を投入する
              2. メニューから「月次集計」を開く
              3. ウィンドウの移動もボタン操作もできない「固まり」が起きることを確認する
期待動作    : 集計に多少時間がかかるとしても、画面が固まらないこと。
              また、5万件程度で何十秒もかかならいこと
ヒント      : 「なぜ遅いのか」と「なぜ固まるのか」は別の問題です。両方直してください。
              集計処理のコードがmainブランチの頃とどう違うか…は見ずに(diff禁止!)、
              処理がSQLで行われているか、Javaのループで行われているかに注目してください
必須タスク  : このバグの自動テストは難しいため、代わりに「手動確認の手順」を書き残す。
              修正の前後で集計にかかる時間を測って比較する(System.currentTimeMillis()等で十分)
```
