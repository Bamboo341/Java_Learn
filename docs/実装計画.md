# 実装計画 — Java実践読解教材「家計簿アプリ」

`docs/Spec.md` に基づく段階的な実装計画です。1ステージずつ指示を受けて実装を進め、各ステージの完了時に「完了条件」を検証してからコミット・プッシュします。

## 全体方針

- **ステージ順序は下位層から上位層へ**(モデル → Repository → Service → UI)。各ステージ完了時点で `./gradlew test` がグリーンであることを維持します。
- **設計意図コメント(`// [設計意図]`)は後付けせず、該当コードを書くステージで埋め込みます**(担当ステージは下表参照)。
- **テストも各層の実装と同じステージで書きます**(テストだけ後回しにしない)。
- ドキュメント類はアプリ完成後に書きます(コードが確定してからでないとトレース手順や行番号がずれるため)。
- バグ仕込み(`exercise/bugs`)と最終検証は最後に行います(Spec.md §10 の作成手順どおり)。

### ブランチ運用に関する注意

開発は作業ブランチ(`claude/spec-md-implementation-plan-qk3jl8`)上で進めます。Spec.md は「`main` = 完成版」「`exercise/bugs` は main から分岐」という構成を要求しているため、**ステージ10(バグ仕込み)の前に、作業ブランチを main へマージする必要があります**(PR作成・マージはユーザー側の操作、または明示的な指示が必要です)。

### 検証環境に関する注意

この環境はヘッドレス(ディスプレイなし)のため、GUI の動作確認は `xvfb-run` による起動スモークテスト(起動してクラッシュしないこと)+スクリーンショット確認までを自動で行い、**操作を伴う画面確認(ボタン操作・ダイアログ遷移など)は各ステージ完了時にユーザー側での確認を依頼します**。

ネットワークは Full アクセスに設定済みで、Maven Central(依存ライブラリの取得)には接続できます(ステージ1完了時に確認)。1点だけ注意: Gradle 本体の配布は GitHub Releases 経由のため、このセッションの GitHub リポジトリスコープ制限で `./gradlew` の初回ダウンロードが403になります。対処として、コンテナに同梱の Gradle 8.14.3 を wrapper のキャッシュ(`~/.gradle/wrapper/dists/`)へ手動配置済みです。**コンテナが作り直された場合は同じ手順での再配置が必要です**(学習者の通常環境では問題は起きません)。

## 各ステージの詳細

### ステージ1: プロジェクト基盤

**目的**: `./gradlew run` で起動できる空のプロジェクトを作り、以降のステージの土台にする。

**作業内容**:
- `settings.gradle` / `build.gradle`(Java 21、application プラグイン、H2・JUnit 5 のみ依存)
- Gradle wrapper の生成と同梱(`gradlew` / `gradlew.bat` / `gradle/`)
- `.gitignore`(`data/`・`build/`・`.gradle/` など)
- パッケージ構造 `com.example.kakeibo`(ui / service / repository / model / infra / exception)の作成
- 仮の `Main.java`(空の JFrame を表示する程度。後続ステージで置き換え)

**完了条件**:
- `./gradlew build` が成功する
- `xvfb-run ./gradlew run` でクラッシュせず起動する
- `data/` が .gitignore されている

---

### ステージ2: モデル・例外・DB基盤

**目的**: データの器と DB 初期化の仕組みを作る。初回起動時に schema.sql / data.sql が自動投入される状態にする。

**作業内容**:
- `model/`: `TransactionType`(enum: INCOME / EXPENSE)、`Category`、`Transaction`
- `exception/`: `ValidationException`(検査例外)、`DataAccessException`(非検査例外、SQLException をラップ)
- `infra/DatabaseManager`: H2 ファイルモード(`./data/kakeibo`)への接続管理、テーブル存在チェックによる冪等なスキーマ初期化
- `src/main/resources/schema.sql`: Spec.md §4.3 のテーブル定義
- `src/main/resources/data.sql`: カテゴリ8種程度+直近3ヶ月・50件程度のサンプル取引(集計画面で意味のある分布にする)
- model にロジックがあればテストを追加

**埋め込む設計意図コメント**: 「金額を int(円)で持つ理由」「符号でなく区分(type)で収支を表す理由」

**完了条件**:
- 初回起動で `data/kakeibo` が生成され初期データが入る。2回目の起動でもエラーにならない(冪等)
- `./gradlew test` グリーン

---

### ステージ3: Repository層

**目的**: 永続化を interface と JDBC 実装のペアで作り、H2 in-memory の結合テストで固める。

**作業内容**:
- `TransactionRepository` / `CategoryRepository`(interface)
- `JdbcTransactionRepository` / `JdbcCategoryRepository`(素の JDBC + PreparedStatement)
- 取引のフィルタ検索(年月・カテゴリ・区分の組み合わせ、日付降順)
- 月次集計クエリ(GROUP BY)と集計結果用 DTO(収入合計・支出合計・カテゴリ別支出)
- カテゴリの使用件数チェック用クエリ(ステージ4の「使用中カテゴリ削除禁止」で使用)
- H2 **in-memory モード**での結合テスト(本体のファイルモード DB と分離する理由をテストコメントに明記)

**埋め込む設計意図コメント**: 「Repository を interface にする理由」「PreparedStatement を使う理由」

**完了条件**: `./gradlew test` グリーン(Repository 結合テスト含む)

---

### ステージ4: Service層

**目的**: 業務ロジックとバリデーションを Service に集約し、網羅的なテストで固める。

**作業内容**:
- `TransactionService`: 登録・編集・削除・フィルタ検索・月次集計の窓口。バリデーション(日付形式、金額は正の整数、カテゴリ必須、メモ200文字以内、区分とカテゴリの整合など)
- `CategoryService`: 追加・名称変更・削除(**使用中カテゴリの削除禁止**)、名称重複チェック
- Service テスト(Repository はテスト用インメモリ実装または H2 in-memory で代替)

**テストに関する重要な注意(Spec.md §5)**: 月次集計の日付テストは**意図的に月中の日付のみ**をカバーし、月末・月初の境界値テストは書かない(BUG-03 の教材化のため)。

**埋め込む設計意図コメント**: 「バリデーションを UI でなく Service で行う理由」

**完了条件**: `./gradlew test` グリーン(バリデーション・業務ルールのテストが網羅されている)

---

### ステージ5: UI — メイン画面と手動DI

**目的**: メイン画面(一覧・フィルタ・ステータスバー)と、Main での手動コンストラクタインジェクションによる全体の組み立て。

**作業内容**:
- `Main.java`: DatabaseManager → Repository → Service → MainFrame の手動DI(仮実装を置き換え)
- `MainFrame`: 上部フィルタ(年月コンボ・カテゴリコンボ・区分ラジオ)、中央 JTable(日付降順)、下部ボタン(登録・編集・削除)、ステータスバー(件数・合計金額)、メニューバー(カテゴリ管理・月次集計 — ダイアログはステージ6まで未接続でよい)
- `TransactionTableModel`: JTable 用モデル+**単体テスト**(Frame/Dialog をテストしない理由をテストコメントに明記)
- UI レイヤでの例外捕捉 → ユーザ向けメッセージ変換の枠組み

**完了条件**:
- `./gradlew test` グリーン
- `xvfb-run` で起動し、一覧に初期データが表示されている(スクリーンショットで確認)
- フィルタ操作・削除ボタンの動作はユーザー側で確認依頼

---

### ステージ6: UI — ダイアログ群(アプリ完成)

**目的**: 残りの画面をすべて実装し、v1.0 の全機能を完成させる。

**作業内容**:
- `TransactionDialog`: 登録・編集のモーダル。日付テキスト(yyyy-MM-dd)、区分ラジオ、**区分に連動して選択肢が変わる**カテゴリコンボ、金額、メモ。バリデーションエラーはダイアログ内に表示。金額入力のパース処理(カンマ付き入力の正規化を含む — BUG-02 の仕込み対象になる箇所)
- `CategoryDialog`: カテゴリ一覧+追加・名称変更・削除
- `SummaryDialog`: 年月選択 → 収入合計・支出合計・収支、カテゴリ別支出テーブル(金額降順・構成比%)。**SwingWorker で集計を実行**(EDT をブロックしない)
- 入力値パース等のロジック部分のテスト

**埋め込む設計意図コメント**: 「集計処理で SwingWorker を使う理由」

**完了条件**:
- `./gradlew test` 全件グリーン
- 全機能(登録・編集・削除・フィルタ・カテゴリ管理・集計)が動作する — ユーザー側での通し確認を依頼
- `[設計意図]` コメントが §4.5 の6箇所すべてに存在する(grep で確認)
- 総規模がテスト込み 2,000〜3,000 行程度に収まっている

### ステージ9: 解答集(answers)

**目的**: 解説付き解答を書く。バグ解答はステージ10で仕込む差分と正確に一致させる必要があるため、**バグの仕込み内容(どのファイルをどう変えるか)をこのステージで確定**させてから書く。

**作業内容**:
- `docs/answers/bug-01.md` 〜 `bug-05.md`: 症状の整理 → 調査の思考過程 → 真因 → 修正内容(diff形式)→ 再発防止テスト例(BUG-04/05 は手動確認手順で代替)→ 教訓
- `docs/answers/feature-101.md` 〜 `feature-104.md`: 設計方針 → 変更ファイル一覧 → 実装例 → ハマりどころ
- 各ファイル冒頭にネタバレ注意
- feature の実装例は実際に手元で動かして検証してから記載する(コミットには含めない)

**完了条件**: bug-0X.md の diff がステージ10で仕込む変更の逆操作と一致している。feature の実装例がコンパイル・動作確認済み。
