# Java実践読解教材「家計簿アプリ」作成指示書

## 0. この文書について

これはClaude Codeへの作業指示書である。成果物は単なるアプリケーションではなく、**「読んで・直して・作って学ぶ」学習教材としてのGitリポジトリ一式**である。アプリ本体・学習ドキュメント・演習・解答のすべてを含む。

作業言語: コード内の識別子(クラス名・変数名)は英語、コメント・ドキュメント・コミットメッセージはすべて日本語。

---

## 1. 教材の目的と対象者

- **対象者**: Javaの文法(変数〜クラス、継承、インターフェース、コレクション、例外処理、ラムダの基礎)を一通り学習済みだが、複数クラスで構成された実アプリケーションのコードを読んだり改修したりした経験がない学習者。
- **解決したい課題**: 文法学習と実務の間にある「複数クラスにまたがる処理を追えない」「設計判断の理由が分からない」「例外処理・バリデーション等の実務コードに免疫がない」というギャップ。
- **学習の3段階**:
  - **Phase 1 読む**: 完成品のコードを読解ガイドに沿って読む
  - **Phase 2 直す**: 仕込まれたバグを症状ベースのチケットから修正する
  - **Phase 3 作る**: チケット形式の仕様書に基づき機能追加する
- ドキュメントの文体は初学者向けに平易な「です・ます調」とし、専門用語には短い補足を付けること。

## 4. アプリケーション仕様(v1.0 = mainブランチ)

### 4.1 機能スコープ

実装する機能:

1. 収支の登録・編集・削除(日付、金額、収入/支出区分、カテゴリ、メモ)
2. カテゴリマスタの管理(追加・名称変更・削除。使用中カテゴリの削除は禁止)
3. 取引一覧のフィルタ(年月、カテゴリ、収入/支出区分の組み合わせ)
4. 月次集計(収入合計・支出合計・収支、カテゴリ別支出の金額と構成比)

**意図的に実装しない機能**(Phase 3の演習ネタとして温存する。コードに拡張の布石を入れないこと):
メモのキーワード検索、CSVエクスポート、予算管理、定期取引。

### 4.2 画面仕様

- **MainFrame(メイン画面)**: 上部にフィルタ(年月コンボボックス、カテゴリコンボボックス、区分ラジオ)、中央にJTableの取引一覧(日付降順)、下部に登録・編集・削除ボタン。ステータスバーに表示件数と合計金額。メニューバーから「カテゴリ管理」「月次集計」を開く。
- **TransactionDialog(登録・編集)**: モーダルダイアログ。日付(yyyy-MM-dd のテキスト入力)、区分(ラジオ)、カテゴリ(区分に連動して選択肢が変わるコンボ)、金額、メモ。バリデーションエラーはダイアログ内にメッセージ表示。
- **CategoryDialog(カテゴリ管理)**: カテゴリ一覧+追加・名称変更・削除。
- **SummaryDialog(月次集計)**: 年月を選択すると、収入合計・支出合計・収支、およびカテゴリ別支出テーブル(金額降順、構成比%)を表示。

### 4.3 データモデル

```sql
CREATE TABLE categories (
    id            IDENTITY PRIMARY KEY,
    name          VARCHAR(50) NOT NULL UNIQUE,
    type          VARCHAR(10) NOT NULL,          -- 'INCOME' / 'EXPENSE'
    display_order INT NOT NULL DEFAULT 0
);

CREATE TABLE transactions (
    id               IDENTITY PRIMARY KEY,
    transaction_date DATE NOT NULL,
    amount           INT NOT NULL,               -- 円。常に正の整数(符号は type で表す)
    type             VARCHAR(10) NOT NULL,       -- 'INCOME' / 'EXPENSE'
    category_id      BIGINT NOT NULL REFERENCES categories(id),
    memo             VARCHAR(200),
    created_at       TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

初期データ: カテゴリ(給与・賞与・食費・日用品・交通費・住居費・娯楽・その他 程度)+直近3ヶ月分・50件程度のリアルなサンプル取引。集計画面を開いたとき意味のある表示になるよう金額とカテゴリの分布に配慮する。

### 4.4 アーキテクチャ

- UI(Swing)→ Service(業務ロジック・バリデーション)→ Repository(永続化)の3層。上位層から下位層への一方向依存を厳守する。
- **DIコンテナは使わず、Mainクラスで手動のコンストラクタインジェクション**を行う(依存性注入の「概念」をフレームワークなしで見せるため)。
- Repositoryは `TransactionRepository` / `CategoryRepository` を**interfaceとして定義**し、`JdbcTransactionRepository` 等の実装クラスと分離する。
- 集計はSQL(GROUP BY)で行い、Repositoryが集計結果用のDTOを返す。
- 例外方針: 入力・業務ルール違反は `ValidationException`(検査例外)、DB障害は `DataAccessException`(非検査例外、SQLExceptionをラップ)。UIレイヤで捕捉してユーザ向けメッセージに変換する。

### 4.5 コーディング要件

- 総規模はテスト込みでおおよそ2,000〜3,000行。1クラスが肥大しないよう責務を分ける。
- コードは「きれいすぎず、しかし筋は通っている」水準。過度な抽象化・デザインパターンの披露は禁止。
- **設計意図コメント**: 設計判断の理由を `// [設計意図]` プレフィックス付きコメントで要所に埋め込む(学習者が `[設計意図]` でgrepすると全て読める)。必須の埋め込み箇所:
  - 金額を `int`(円)で持つ理由(doubleの誤差、日本円に小数はない)
  - Repositoryをinterfaceにする理由(差し替え可能性・テスト容易性)
  - PreparedStatementを使う理由(SQLインジェクション)
  - バリデーションをUIでなくServiceで行う理由(UIを信用しない)
  - 集計処理でSwingWorkerを使う理由(EDTをブロックしない)
  - 符号でなく区分(type)で収支を表す理由
- 主要な公開クラス・メソッドには簡潔な日本語Javadocを付ける。

## 5. テスト要件(全層)

- **model**: enumやエンティティのロジックがあればテスト。
- **service**: バリデーション・業務ルールを網羅的にテスト(Repositoryはテスト用のインメモリ実装またはH2 in-memoryで代替)。
- **repository**: H2の**in-memoryモード**を使った結合テスト(本体のファイルモードDBとは分離する。この分離自体が学習ポイントなのでテストコードにコメントで明記)。
- **ui**: `TransactionTableModel` や入力値パース等の**ロジック部分のみ**テストする。Frame/Dialogはテスト対象外とし、その理由(「画面そのもののテストは難しい。だからこそロジックを画面から剥がす」)をテストクラスのコメントに明記する。
- mainブランチでは `./gradlew test` が**全件グリーン**であること。
- **重要**: BUG-03(後述)に対応する日付境界のテストは、**意図的に月中の日付のみをカバー**し、月末・月初の境界値テストを書かないこと(テストの穴を教材化するため)。

## 6. 学習ドキュメント要件(docs/)

### 00_はじめに.md
教材の目的、対象者、3つのPhaseの進め方、JDKインストールと `./gradlew run` での起動手順、まず10分アプリを触ってみる案内。

### 01_読解マップ.md(Phase 1)
1. **全体地図**: 3層アーキテクチャの説明と、パッケージ間依存のMermaid図。
2. **縦断トレース**: ユースケース「支出を1件登録する」を、登録ボタンのクリック→ActionListener→Dialogの入力取得→Service(バリデーション)→Repository(INSERT)→一覧の再読込、までファイル名・メソッド名付きの番号付き手順で追わせる。各ステップに「ここで何をしているか自分の言葉で書く」記入欄を設ける。
3. **責務ワークシート**: 全クラスの一覧表に「このクラスの責務を一言で」を書き込ませる。
4. **発展読解課題**: 「編集・削除の流れを自力でトレースせよ」「月次集計のSQLを読んで日本語で説明せよ」「`[設計意図]` コメントを全部探して読め」。

### 02_バグ修正演習.md(Phase 2)
- `git checkout exercise/bugs` の手順と、演習の進め方(①症状を再現 ②仮説を立てる ③デバッガ/ログ/テストで検証 ④修正 ⑤**再発防止テストを追加** ⑥answersと照合)。
- デバッガの使い方(ブレークポイント、ステップ実行)とスタックトレースの読み方の簡単な入門を含める。
- BUG-01〜05のチケットを記載。チケットは実務風のフォーマットで書く:

```
チケット番号: BUG-01
報告者: 経理担当・佐藤
症状: 使わなくなったカテゴリを削除しようとしたらアプリがエラーで固まった
再現手順: 1. カテゴリ管理を開く 2. 取引で使用中のカテゴリを選ぶ 3. 削除ボタン
期待動作: 「使用中のため削除できません」と案内されること
ヒント: まず ./gradlew test を実行してみてください
```

### 03_機能追加演習.md(Phase 3)
`main` に戻る手順と、T-101〜T-104のチケット(実務の仕様書風に、受け入れ条件を明記)。

### 04_大量データ投入.md
BUG-05の再現とT-103の動作確認用に、5万件のダミー取引を生成するSQL(H2の `SYSTEM_RANGE` 等を利用)と投入・削除手順。

### answers/(解説付き解答)
- 冒頭にネタバレ注意の警告を置く。
- **バグ解答(bug-0X.md)**: 症状の整理 → 調査の進め方(どう当たりを付け、どのツールでどう突き止めるかの思考過程) → 真因の解説 → 修正内容(diff形式) → 再発防止テストの例 → この型のバグから得る教訓。
- **機能解答(feature-10X.md)**: 設計方針(なぜその置き場所か) → 変更ファイル一覧 → 実装例 → ハマりどころ。

## 7. バグ仕込み仕様(exercise/bugs ブランチ)

| ID | 症状(チケットの内容) | 真因 | テストとの関係 | 学習ポイント |
|---|---|---|---|---|
| BUG-01 | 使用中カテゴリを削除するとアプリがクラッシュする | `CategoryService` の使用中チェックを削除 → FK違反の `SQLException` が未処理で貫通 | **`./gradlew test` で該当テストが赤になる(唯一テストで検知可能)** | テスト実行→赤→スタックトレース→該当コード、という実務の入口ワークフロー |
| BUG-02 | 金額に「1,000」とカンマ付きで入力するとエラーで落ちる | `TransactionDialog` 内のprivateなパース処理から入力正規化を削除 → 未捕捉 `NumberFormatException` | すり抜け(UI内のprivateメソッドでテスト対象外) | 実行時例外の追跡、防御的な入力処理。解答で「テストできる場所に切り出すべき」というリファクタ提案まで繋げる |
| BUG-03 | 1月31日の支出が1月の月次集計に含まれない | 集計の日付範囲条件の境界ミス(`<=` を `<` にする等) | すり抜け(テストが月中の日付しかカバーしていない) | 境界値バグ、「テストが緑=バグがない、ではない」。修正後に境界値テストを追加させる |
| BUG-04 | 取引を編集して保存しても一覧が変わらない。アプリを再起動すると変わっている | 編集後の `TableModel` 更新通知(または再読込)の呼び出しを削除 | すり抜け(画面の振る舞いは単体テストの射程外) | 「データは正しいのに表示が古い」の切り分け、Swingの更新通知機構 |
| BUG-05 | 月次集計を開くと画面全体が数秒〜数十秒固まる(大量データ投入後) | SQL集計を「全件ロード+1件ずつカテゴリを都度SELECT(N+1)」のJavaループに書き換え、かつEDT上で直接実行(SwingWorkerを外す) | すり抜け(性能問題は単体テストで検知しにくい) | EDTとUIフリーズ、N+1問題、SwingWorkerによる修正。データ量で顕在化する性能バグの実務感 |

- 各チケットの必須タスクに「修正後、再発防止テストを追加する(可能なもののみ。BUG-04/05は手動確認手順の記述で代替)」を含める。
- バグ以外のコード・ドキュメントはmainと完全に同一に保つ。

## 10. 作成手順と品質チェックリスト

作成手順: ① mainブランチでアプリ+テスト+全ドキュメントを完成させる → ② 動作確認 → ③ `exercise/bugs` を分岐し5バグを単一コミットで仕込む → ④ 両ブランチで最終確認。

完成時に以下をすべて検証すること:

- [ ] クリーンな環境で `git clone` 相当の状態から `./gradlew run` のみで起動する
- [ ] main: 全機能(登録・編集・削除・フィルタ・カテゴリ管理・集計)が動作する
- [ ] main: `./gradlew test` が全件グリーン
- [ ] exercise/bugs: `./gradlew test` で**BUG-01関連のテストのみ**が赤、他はグリーン
- [ ] exercise/bugs: 5つのバグすべてがチケットの再現手順どおりに症状を再現する(BUG-05は大量データ投入後)
- [ ] `[設計意図]` コメントが4.5節の指定箇所すべてに存在する
- [ ] docs一式・answers一式が揃っており、手順どおりに学習を進められる
- [ ] `data/` ディレクトリが .gitignore されている
